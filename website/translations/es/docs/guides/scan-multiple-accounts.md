# Analizar varias cuentas

**Para quién es:** te encargas de más de una cuenta de AWS y quieres un informe
consolidado.

**Qué podrás hacer después de leerlo:** listar tus cuentas una vez y analizarlas
todas en una sola ejecución.

## Cómo funciona {#how-it-works}

InvenTag lee una lista de cuentas. Para cada una obtiene credenciales, ya sea
de un perfil con nombre de la CLI de AWS o asumiendo un rol de IAM desde la
identidad con la que lo ejecutas. Analiza cada cuenta, hasta cuatro a la vez
por defecto, y escribe un único informe con una columna Account.

InvenTag no lista por ti las cuentas de tu AWS Organization. Tú escribes la
lista.

## 1. Crea un rol de solo lectura en cada cuenta {#1-create-a-read-only-role-in-every-account}

Sigue [Configurar el acceso de solo lectura](./read-only-access.md#with-an-iam-role-in-each-account).
Usa el mismo nombre de rol en todas partes, por ejemplo `InvenTagReadOnly`.

## 2. Obtén tu lista de cuentas {#2-get-your-account-list}

Desde la cuenta de administración, o una cuenta de administrador delegado:

```bash
aws organizations list-accounts \
  --query "Accounts[?Status=='ACTIVE'].[Id,Name]" --output text
```

## 3. Escribe la lista como plantilla de configuración {#3-write-the-list-as-a-config-template}

```bash
inventag templates init org-multi-account --output .inventag/templates/our-org.yaml
```

Edita la sección `accounts`. Cada cuenta necesita su ID de 12 dígitos **entre
comillas** y un `role_arn` o un `profile_name`:

```yaml
spec:
  accounts:
    - account_id: "123456789012"
      account_name: Production
      role_arn: arn:aws:iam::123456789012:role/InvenTagReadOnly
    - account_id: "210987654321"
      account_name: Development
      profile_name: dev-readonly
  regions: [us-east-1, eu-west-1]
```

Compruébala y después ejecútala:

```bash
inventag templates validate our-org
inventag --template our-org
```

`validate` detecta los errores más comunes: IDs de cuenta sin comillas, un ARN
de rol que apunta a una cuenta distinta de `account_id` y claves de acceso en
el archivo (no se permiten en las plantillas). Con los IDs de marcador de
posición aún presentes dice (datos de ejemplo):

```text title="Salida"
WARNING ~/acme-infra/.inventag/templates/our-org.yaml: account IDs 111111111111, 222222222222, 333333333333 look like placeholders; replace them with your own
OK    ~/acme-infra/.inventag/templates/our-org.yaml (config 'our-org')
```

Una ejecución sobre las tres cuentas de ejemplo:

```text title="Salida"
Wrote bom_output/tag_compliance_20261112_090000.json
Wrote bom_output/multi_account_bom_20261112_090000.docx
Wrote bom_output/multi_account_bom_20261112_090000.xlsx
Tag policy 'finops-cost-allocation': 0 of 39 resources compliant (0.0%), 39 non-compliant, 42 out of scope.
```

**Hojas:** `Summary`, `ATHENA`, `EVENTS`, `KMS`, `S3`, `VPC`, `Tag Compliance`

Hoja `Summary`:

> AWS Resource Inventory  
> Bill of materials generated by InvenTag  
> Generated: 2026-11-12 09:00 UTC  
> Accounts: 3   Regions: 1  

| Service | Resources | Share |
|---|---|---|
| ATHENA | 3 | 3.7% |
| EVENTS | 3 | 3.7% |
| KMS | 42 | 51.9% |
| S3 | 3 | 3.7% |

## O usa un archivo de cuentas {#or-use-an-accounts-file}

La opción `--accounts-file` también funciona y acepta claves de acceso (evítalas
si puedes). Si todas las cuentas usan el mismo nombre de rol, no necesitas
escribir cada ARN:

```bash title="Terminal"
inventag --accounts-file accounts.yaml --cross-account-role InvenTagReadOnly --create-excel
```

El formato del archivo de cuentas está en [Archivos de configuración](../reference/configuration-files.md#accounts-file).

```bash
inventag --accounts-file accounts.yaml --create-excel
```

## Ajusta la ejecución {#tune-the-run}

| Ajuste | Campo de la plantilla de configuración | Opción |
|---|---|---|
| Cuentas analizadas a la vez (por defecto 4) | `max_concurrent_accounts` | `--max-concurrent-accounts` |
| Segundos permitidos por cuenta (por defecto 1800, al menos 60) | `account_processing_timeout` | `--account-processing-timeout` |
| Una cuenta cada vez | `parallel_processing: false` | `--disable-parallel-processing` |

Si una cuenta falla, por ejemplo porque no se puede asumir su rol, InvenTag
registra el error e informa de las cuentas que funcionaron. No recurre a tus
credenciales predeterminadas para esa cuenta. La hoja `Summary` del informe de
Excel y el informe de Word tienen una sección «Run notes» (notas de la ejecución) que nombra cada cuenta que no se analizó y por qué.
El registro tiene la misma lista:

```text
1 account(s) were not scanned, or only partly. The report does not include them:
  - 222222222222 (Dev): Context establishment failed: Role assumption failed for account 222222222222: An error occurred (AccessDenied) when calling the AssumeRole operation: ...
```

La ejecución sigue terminando con el código 0. Añade `--fail-on-account-error` para terminar con el código 5
cuando alguna cuenta no se haya podido analizar por completo. Los informes se escriben igualmente.
Si todas las cuentas fallan, la ejecución termina con el código 1 y no escribe ningún informe.

Una cuenta que se queda sin tiempo (`--account-processing-timeout`) cuenta como fallida, pero los recursos que encontró
antes del límite siguen en el informe, y las notas indican que la cuenta está incompleta.
Consulta [Límite de tiempo y cuentas en paralelo](./run-a-scan.md#time-limit-and-parallel-accounts).

## Continúa tras un fallo {#continue-after-a-failure}

InvenTag guarda las cuentas que terminaron. Cuando corrijas la causa, ejecuta el mismo comando con `--resume` para analizar solo las demás:

```bash
inventag --accounts-file accounts.yaml --create-excel --resume
```

InvenTag reutiliza los resultados guardados del mismo comando (mismas cuentas, regiones, servicios y filtros) que no sean
más antiguos que `--resume-max-age-hours` (por defecto 24, como máximo 168).
Consulta [Continúa tras una ejecución fallida](./run-a-scan.md#continue-after-a-failed-run).

## En un pipeline de GitLab CI/CD {#in-a-gitlab-cicd-pipeline}

No verificado contra un runner de GitLab ni una cuenta real de AWS: este pipeline no se ha ejecutado en GitLab. Su YAML y su línea de comandos de `inventag` se comprueban al compilar la documentación. Su job se ejecutó en local con gitlab-ci-local 4.77.1 (con un sustituto de rsync) contra un AWS simulado, con un token ficticio.

Este job analiza todas las cuentas de `accounts.yaml` en una programación de pipelines. Inicia sesión en un solo rol mediante OIDC, y después InvenTag asume el rol `InvenTagReadOnly` en cada cuenta. El job usa `--resume`, así que la caché y un **Retry** pueden terminar las cuentas que faltaban. `accounts.yaml` está en el repositorio, por lo que solo debe contener IDs y nombres de cuenta, y ninguna clave de acceso. Antes de usarlo:

- Crea el rol con el que GitLab inicia sesión y la variable de CI/CD `AWS_ROLE_ARN`, como se describe en [Ejecutar InvenTag en CI/CD](../guides/run-in-ci.md#gitlab-cicd). Esa misma sección explica cómo crear la programación del pipeline.
- Da a ese rol `sts:AssumeRole` sobre el rol `InvenTagReadOnly` de cada cuenta, y haz que cada uno de esos roles confíe en él: consulta [Configurar el acceso de solo lectura](./read-only-access.md#with-an-iam-role-in-each-account). El archivo de política `config/defaults/iam-policy-read-only.json` no tiene ninguna declaración `sts:AssumeRole`, así que la añades tú.

```yaml
# .gitlab-ci.yml
stages:
  - inventory

org-inventory:
  stage: inventory
  image: python:3.12
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule"
    - if: $CI_PIPELINE_SOURCE == "web"
  timeout: 3 hours                            # the ID token expires with the job
  id_tokens:
    GITLAB_OIDC_TOKEN:
      aud: sts.amazonaws.com
  variables:
    AWS_DEFAULT_REGION: us-east-1
  cache:
    key: inventag-state
    paths:
      - bom_output/state/                     # saved results of finished accounts, for --resume
    when: always                              # save them when the job fails, too
  script:
    - pip install "inventag-aws==%INVENTAG_VERSION%"   # pin a release
    - export AWS_WEB_IDENTITY_TOKEN_FILE="$(mktemp)"
    - printf '%s' "$GITLAB_OIDC_TOKEN" > "$AWS_WEB_IDENTITY_TOKEN_FILE"
    - |
      inventag --accounts-file accounts.yaml --cross-account-role InvenTagReadOnly \
        --create-excel --resume --resume-max-age-hours 12 \
        --fail-on-account-error --fail-if-empty
  artifacts:
    when: always                              # keep the reports of the accounts that worked
    paths:
      - bom_output/
    expire_in: 30 days
```

Las líneas que comparten todos los ejemplos de GitLab se explican en [Ejecutar InvenTag en CI/CD](../guides/run-in-ci.md#gitlab-cicd). Esta tabla cubre lo que es propio de este ejemplo.

| Parte | Qué hace |
|---|---|
| `--accounts-file accounts.yaml --cross-account-role InvenTagReadOnly` | El job inicia sesión en un solo rol mediante OIDC. Desde ahí, InvenTag asume el rol `InvenTagReadOnly` en cada cuenta del archivo. |
| `cache:` con `key: inventag-state`, `paths: - bom_output/state/`, `when: always` | InvenTag guarda las cuentas que terminaron en `bom_output/state/partial/` ([Continúa tras una ejecución fallida](./run-a-scan.md#continue-after-a-failed-run)). Un job nuevo empieza con una carpeta vacía, así que la caché lleva `bom_output/state/` al job siguiente. `when: always` guarda la caché cuando el job falla; por defecto solo se guarda si tiene éxito ([GitLab: `cache:when`](https://docs.gitlab.com/ci/yaml/#cachewhen), [GitLab: caching](https://docs.gitlab.com/ci/caching/)). |
| `--resume --resume-max-age-hours 12` | Tras una ejecución fallida, pulsa **Retry** en el job (o espera a la siguiente ejecución): solo se analizan las cuentas que faltan. El `12` es a propósito. Con el valor predeterminado de 24 horas, la ejecución de la noche siguiente podría reutilizar los resultados de la noche anterior de una ejecución que falló. Sin resultados guardados, `--resume` no cambia nada. Si la caché no está, se vuelven a analizar todas las cuentas: más lento, nunca incorrecto. Las reglas para reutilizar resultados guardados están en [Continúa tras una ejecución fallida](./run-a-scan.md#continue-after-a-failed-run). |
| `--fail-on-account-error --fail-if-empty` | Código de salida 5 cuando no se pudo analizar una cuenta; código de salida 6 cuando no se encontró ningún recurso. Los informes de las demás cuentas se escriben y los conserva `artifacts: when: always` ([GitLab: `artifacts:when`](https://docs.gitlab.com/ci/yaml/#artifactswhen)). |
| `timeout: 3 hours` | Lo máximo que puede durar un job en los runners alojados por GitLab de GitLab.com ([GitLab: hosted runners](https://docs.gitlab.com/ci/runners/hosted_runners/)). |

Partes que la ejecución local no cubrió:

- No verificado contra GitLab ni AWS: que GitLab emita el token de ID y que AWS lo acepte para el rol, con las condiciones de la política de confianza sobre `aud` y `sub`.
- No verificado contra GitLab: `image`, `timeout`, `expire_in` y `cache` (gitlab-ci-local los ignora).
- No verificado contra una programación de pipelines de GitLab: la ejecución en local fijó a mano el origen del pipeline.
- No verificado contra AWS: que el rol de OIDC asuma el rol `InvenTagReadOnly` en cada cuenta, con políticas de confianza reales.

## Comprueba el archivo de cuentas {#check-the-accounts-file}

InvenTag lee el archivo de cuentas como texto UTF-8, con o sin marca de orden de bytes, de hasta 1 MiB.
Se detiene con código de salida 1 y nombra el problema cuando:

- el archivo está vacío, o su nivel superior es una lista y no un conjunto de pares `clave: valor`;
- una clave está escrita dos veces (el mensaje indica la línea, por ejemplo `accounts file accounts.yaml:3: duplicate key 'accounts'`);
- el tipo de archivo no es `.json`, `.yaml` ni `.yml`;
- una cuenta no tiene un `account_id` no vacío, o un campo tiene el tipo equivocado.

Si el archivo contiene `secret_access_key` o `session_token` y otros usuarios pueden leerlo, InvenTag avisa y te indica que ejecutes `chmod 600`.
Usa `profile_name` o `role_arn` en lugar de claves. Comprueba un archivo sin analizar:
`inventag --accounts-file accounts.yaml --validate-config-only --skip-credential-validation`.

Dos errores de opciones detienen la ejecución con código de salida 2: `--accounts-file` junto con `--accounts-prompt`,
y un ARN de rol completo en `--cross-account-role` junto con un archivo de cuentas (indica ahí un nombre de rol, o pon `role_arn` en el archivo).
