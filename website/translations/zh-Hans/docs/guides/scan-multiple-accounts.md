# 扫描多个账户

**适合谁阅读：** 你管理不止一个 AWS 账户，想得到一份合并的报告。

**读完后你可以：** 把账户列出一次，并在一次运行中全部扫描。

## 工作原理 {#how-it-works}

InvenTag 读取一份账户列表。对每个账户，它要么从指定的 AWS CLI 配置文件（profile）获取凭证，
要么用你运行它时所用的身份去代入一个 IAM 角色。它会扫描每个账户（默认最多同时扫描四个），
并写出一份带有 Account 列的报告。

InvenTag 不会替你列出 AWS Organization 中的账户。这份列表需要你自己写。

## 1. 在每个账户中创建只读角色 {#1-create-a-read-only-role-in-every-account}

请按照[设置只读访问](./read-only-access.md#with-an-iam-role-in-each-account)操作。
所有账户使用同一个角色名称，例如 `InvenTagReadOnly`。

## 2. 获取账户列表 {#2-get-your-account-list}

在管理账户或委派管理员账户中：

```bash
aws organizations list-accounts \
  --query "Accounts[?Status=='ACTIVE'].[Id,Name]" --output text
```

## 3. 把列表写成配置模板 {#3-write-the-list-as-a-config-template}

```bash
inventag templates init org-multi-account --output .inventag/templates/our-org.yaml
```

编辑 `accounts` 部分。每个账户都需要它的 12 位 ID（**要加引号**），
以及 `role_arn` 或 `profile_name` 之一：

```yaml
spec:
  accounts:
    - account_id: "123456789012"
      account_name: Production
      role_arn: arn:aws:iam::123456789012:role/InvenTagReadOnly
    - account_id: "210987654321"
      account_name: Development
      profile_name: dev-readonly
  regions: [us-east-1, eu-west-1]
```

先检查，再运行：

```bash
inventag templates validate our-org
inventag --template our-org
```

`validate` 能发现常见的错误：没有加引号的账户 ID、指向与 `account_id` 不同账户的角色 ARN，
以及文件中的访问密钥（模板中不允许）。如果仍保留着占位符 ID，它会提示（示例数据）：

```text title="输出"
WARNING ~/acme-infra/.inventag/templates/our-org.yaml: account IDs 111111111111, 222222222222, 333333333333 look like placeholders; replace them with your own
OK    ~/acme-infra/.inventag/templates/our-org.yaml (config 'our-org')
```

针对三个示例账户的一次运行：

```text title="输出"
Wrote bom_output/tag_compliance_20261112_090000.json
Wrote bom_output/multi_account_bom_20261112_090000.docx
Wrote bom_output/multi_account_bom_20261112_090000.xlsx
Tag policy 'finops-cost-allocation': 0 of 39 resources compliant (0.0%), 39 non-compliant, 42 out of scope.
```

**工作表：** `Summary`、`ATHENA`、`EVENTS`、`KMS`、`S3`、`VPC`、`Tag Compliance`

`Summary` 工作表：

> AWS Resource Inventory  
> Bill of materials generated by InvenTag  
> Generated: 2026-11-12 09:00 UTC  
> Accounts: 3   Regions: 1  

| Service | Resources | Share |

| ATHENA | 3 | 3.7% |
| EVENTS | 3 | 3.7% |

## 或者使用账户文件 {#or-use-an-accounts-file}

`--accounts-file` 选项同样可用，并且它接受访问密钥（如果可以，请避免使用）。
如果每个账户使用相同的角色名称，就不需要逐个写出 ARN：

```bash title="Terminal"
inventag --accounts-file accounts.yaml --cross-account-role InvenTagReadOnly --create-excel
```

账户文件的格式见[配置文件](../reference/configuration-files.md#accounts-file)。

```bash
inventag --accounts-file accounts.yaml --create-excel
```

## 调整运行 {#tune-the-run}

| 设置 | 配置模板字段 | 参数 |
|---|---|---|
| 同时扫描的账户数（默认 4） | `max_concurrent_accounts` | `--max-concurrent-accounts` |
| 每个账户允许的秒数（默认 1800，至少 60） | `account_processing_timeout` | `--account-processing-timeout` |
| 一次一个账户 | `parallel_processing: false` | `--disable-parallel-processing` |

如果某个账户失败，例如因为无法代入它的角色，InvenTag 会记录错误，并报告成功的那些账户。
它不会对该账户回退到你的默认凭证。Excel 报告的 `Summary` 工作表和 Word 报告都有“运行备注”（Run notes）部分，
列出每个未被扫描的账户及原因。日志中有同样的列表：

```text
1 account(s) were not scanned, or only partly. The report does not include them:
  - 222222222222 (Dev): Context establishment failed: Role assumption failed for account 222222222222: An error occurred (AccessDenied) when calling the AssumeRole operation: ...
```

运行仍然以退出码 0 结束。加上 `--fail-on-account-error`，当有账户无法完整扫描时会以退出码 5 结束。报告仍会写出。
如果所有账户都失败，运行会以退出码 1 结束，并且不写出任何报告。

超时的账户（`--account-processing-timeout`）算作失败，但它在限制之前找到的资源仍留在报告中，备注会说明该账户不完整。
见[时间限制与并行账户](./run-a-scan.md#time-limit-and-parallel-accounts)。

## 失败之后继续 {#continue-after-a-failure}

InvenTag 会保存已完成的账户。排除原因后，用同一条命令加上 `--resume`，只扫描其余账户：

```bash
inventag --accounts-file accounts.yaml --create-excel --resume
```

InvenTag 会复用同一条命令（相同的账户、区域、服务和筛选条件）保存的、不早于 `--resume-max-age-hours`（默认 24，最多 168）的结果。
见[失败的运行之后继续](./run-a-scan.md#continue-after-a-failed-run)。

## 在 GitLab CI/CD 流水线中 {#in-a-gitlab-cicd-pipeline}

未针对 GitLab Runner 或真实的 AWS 账户验证：此流水线尚未在 GitLab 上运行。它的 YAML 和 `inventag` 命令行会在构建文档时检查。它的作业已在本地用 gitlab-ci-local 4.77.1（用替身代替 rsync）针对模拟的 AWS 运行，使用的是虚拟令牌。

这个作业按流水线计划扫描 `accounts.yaml` 中的每个账户。它通过 OIDC 登录到一个角色，然后 InvenTag 在每个账户中担任 `InvenTagReadOnly` 角色。该作业使用 `--resume`，所以缓存加上一次 **Retry** 就能完成之前缺少的账户。`accounts.yaml` 会提交到仓库，因此它只能包含账户 ID 和名称，不能包含访问密钥。使用之前：

- 按照[在 CI/CD 中运行 InvenTag](../guides/run-in-ci.md#gitlab-cicd)中的说明，创建 GitLab 用来登录的角色和 CI/CD 变量 `AWS_ROLE_ARN`。该部分也说明了如何创建流水线计划。
- 给该角色授予对每个账户中 `InvenTagReadOnly` 角色的 `sts:AssumeRole` 权限，并让这些角色都信任它：见[设置只读访问](./read-only-access.md#with-an-iam-role-in-each-account)。策略文件 `config/defaults/iam-policy-read-only.json` 中没有 `sts:AssumeRole` 语句，所以需要你自己添加。

```yaml
# .gitlab-ci.yml
stages:
  - inventory

org-inventory:
  stage: inventory
  image: python:3.12
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule"
    - if: $CI_PIPELINE_SOURCE == "web"
  timeout: 3 hours                            # the ID token expires with the job
  id_tokens:
    GITLAB_OIDC_TOKEN:
      aud: sts.amazonaws.com
  variables:
    AWS_DEFAULT_REGION: us-east-1
  cache:
    key: inventag-state
    paths:
      - bom_output/state/                     # saved results of finished accounts, for --resume
    when: always                              # save them when the job fails, too
  script:
    - pip install "inventag-aws==%INVENTAG_VERSION%"   # pin a release
    - export AWS_WEB_IDENTITY_TOKEN_FILE="$(mktemp)"
    - printf '%s' "$GITLAB_OIDC_TOKEN" > "$AWS_WEB_IDENTITY_TOKEN_FILE"
    - |
      inventag --accounts-file accounts.yaml --cross-account-role InvenTagReadOnly \
        --create-excel --resume --resume-max-age-hours 12 \
        --fail-on-account-error --fail-if-empty
  artifacts:
    when: always                              # keep the reports of the accounts that worked
    paths:
      - bom_output/
    expire_in: 30 days
```

所有 GitLab 示例共有的行，在[在 CI/CD 中运行 InvenTag](../guides/run-in-ci.md#gitlab-cicd)中说明。下表只说明这个示例特有的部分。

| 部分 | 作用 |
|---|---|
| `--accounts-file accounts.yaml --cross-account-role InvenTagReadOnly` | 作业通过 OIDC 登录到一个角色。InvenTag 再从该角色出发，在文件中的每个账户里担任 `InvenTagReadOnly` 角色。 |
| `cache:`，带 `key: inventag-state`、`paths: - bom_output/state/`、`when: always` | InvenTag 会把已完成的账户保存在 `bom_output/state/partial/`（[失败的运行之后继续](./run-a-scan.md#continue-after-a-failed-run)）。新的作业从空文件夹开始，所以由缓存把 `bom_output/state/` 带给下一个作业。`when: always` 让作业失败时也保存缓存；默认只在成功时保存（[GitLab：`cache:when`](https://docs.gitlab.com/ci/yaml/#cachewhen)、[GitLab：缓存](https://docs.gitlab.com/ci/caching/)）。 |
| `--resume --resume-max-age-hours 12` | 运行失败后，在作业上点击 **Retry**（或等待下一次运行）：只会扫描缺少的账户。选择 `12` 是有意的。若使用默认的 24 小时，下一个夜间运行可能会重用上一晚失败那次运行的结果。没有已保存的结果时，`--resume` 不起任何作用。如果缓存不在，就会重新扫描每个账户：更慢，但不会出错。重用已保存结果的规则见[失败的运行之后继续](./run-a-scan.md#continue-after-a-failed-run)。 |
| `--fail-on-account-error --fail-if-empty` | 有账户无法扫描时，退出码为 5；没有找到任何资源时，退出码为 6。其他账户的报告会被写出，并由 `artifacts: when: always` 保留（[GitLab：`artifacts:when`](https://docs.gitlab.com/ci/yaml/#artifactswhen)）。 |
| `timeout: 3 hours` | 作业在 GitLab.com 的 GitLab 托管 Runner 上最长可以运行的时间（[GitLab：托管 Runner](https://docs.gitlab.com/ci/runners/hosted_runners/)）。 |

本地运行没有覆盖的部分：

- 未针对 GitLab 或 AWS 验证：GitLab 签发 ID 令牌，以及 AWS 为该角色接受它，包括信任策略中对 `aud` 和 `sub` 的条件。
- 未针对 GitLab 验证：`image`、`timeout`、`expire_in` 和 `cache`（gitlab-ci-local 会忽略它们）。
- 未针对 GitLab 流水线计划验证：本地运行时，流水线来源是手动设置的。
- 未针对 AWS 验证：OIDC 角色在每个账户中担任 `InvenTagReadOnly` 角色，使用真实的信任策略。

## 检查账户文件 {#check-the-accounts-file}

InvenTag 以 UTF-8 文本读取账户文件（有无字节顺序标记均可），文件不能超过 1 MiB。出现以下情况时，它会以退出码 1 停止并指出问题：

- 文件为空，或顶层是列表而不是一组 `key: value`；
- 某个键写了两次（消息会给出行号，例如 `accounts file accounts.yaml:3: duplicate key 'accounts'`）；
- 文件类型不是 `.json`、`.yaml` 或 `.yml`；
- 某个账户没有非空的 `account_id`，或某个字段的类型不对。

如果文件中有 `secret_access_key` 或 `session_token`，并且其他用户可以读取它，InvenTag 会发出警告，提示你运行 `chmod 600`。
请使用 `profile_name` 或 `role_arn`，而不要使用密钥。不扫描也能检查文件：
`inventag --accounts-file accounts.yaml --validate-config-only --skip-credential-validation`。

有两种选项错误会让运行以退出码 2 停止：`--accounts-file` 与 `--accounts-prompt` 同时给出，
以及 `--cross-account-role` 中的完整角色 ARN 与账户文件同用（那里应给角色名，或在文件中写 `role_arn`）。
