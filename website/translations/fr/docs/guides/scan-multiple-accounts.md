# Analyser plusieurs comptes

**À qui s’adresse cette page :** vous gérez plusieurs comptes AWS et vous voulez un seul rapport
consolidé.

**Ce que vous saurez faire après lecture :** lister vos comptes une fois et les analyser tous
en une seule exécution.

## Comment ça marche {#how-it-works}

InvenTag lit une liste de comptes. Pour chacun, il obtient des identifiants, soit
à partir d’un profil AWS CLI nommé, soit en assumant un rôle IAM depuis l’identité avec laquelle vous
l’exécutez. Il analyse chaque compte, quatre à la fois par défaut, et
écrit un seul rapport avec une colonne Account.

InvenTag ne liste pas pour vous les comptes de votre AWS Organization. Vous
écrivez la liste.

## 1. Créer un rôle en lecture seule dans chaque compte {#1-create-a-read-only-role-in-every-account}

Suivez [Configurer un accès en lecture seule](./read-only-access.md#with-an-iam-role-in-each-account).
Utilisez le même nom de rôle partout, par exemple `InvenTagReadOnly`.

## 2. Obtenir votre liste de comptes {#2-get-your-account-list}

Depuis le compte de gestion, ou un compte d’administrateur délégué :

```bash
aws organizations list-accounts \
  --query "Accounts[?Status=='ACTIVE'].[Id,Name]" --output text
```

## 3. Écrire la liste sous forme de modèle de configuration {#3-write-the-list-as-a-config-template}

```bash
inventag templates init org-multi-account --output .inventag/templates/our-org.yaml
```

Modifiez la section `accounts`. Chaque compte a besoin de son identifiant à 12 chiffres **entre guillemets**
et d’un `role_arn` ou d’un `profile_name` :

```yaml
spec:
  accounts:
    - account_id: "123456789012"
      account_name: Production
      role_arn: arn:aws:iam::123456789012:role/InvenTagReadOnly
    - account_id: "210987654321"
      account_name: Development
      profile_name: dev-readonly
  regions: [us-east-1, eu-west-1]
```

Vérifiez-le, puis lancez l’analyse :

```bash
inventag templates validate our-org
inventag --template our-org
```

`validate` détecte les erreurs courantes : identifiants de compte sans guillemets, ARN de rôle qui
pointe vers un autre compte que `account_id`, et clés d’accès dans le fichier
(interdites dans les modèles). Avec les identifiants fictifs encore en place, il affiche
(données d’exemple) :

```text title="Sortie"
WARNING ~/acme-infra/.inventag/templates/our-org.yaml: account IDs 111111111111, 222222222222, 333333333333 look like placeholders; replace them with your own
OK    ~/acme-infra/.inventag/templates/our-org.yaml (config 'our-org')
```

Une exécution sur les trois comptes d’exemple :

```text title="Sortie"
Wrote bom_output/tag_compliance_20261112_090000.json
Wrote bom_output/multi_account_bom_20261112_090000.docx
Wrote bom_output/multi_account_bom_20261112_090000.xlsx
Tag policy 'finops-cost-allocation': 0 of 39 resources compliant (0.0%), 39 non-compliant, 42 out of scope.
```

**Feuilles :** `Summary`, `ATHENA`, `EVENTS`, `KMS`, `S3`, `VPC`, `Tag Compliance`

Feuille `Summary` :

> AWS Resource Inventory

> Generated: 2026-11-12 09:00 UTC  
> Accounts: 3   Regions: 1  

| Service | Resources | Share |
|---|---|---|

| EVENTS | 3 | 3.7% |

## Ou utiliser un fichier de comptes {#or-use-an-accounts-file}

L’option `--accounts-file` fonctionne aussi, et elle accepte des clés d’accès (évitez-les
si possible). Si tous les comptes utilisent le même nom de rôle, vous n’avez pas besoin d’écrire
chaque ARN :

```bash title="Terminal"
inventag --accounts-file accounts.yaml --cross-account-role InvenTagReadOnly --create-excel
```

Le format du fichier de comptes est décrit dans [Fichiers de configuration](../reference/configuration-files.md#accounts-file).

```bash
inventag --accounts-file accounts.yaml --create-excel
```

## Ajuster l’exécution {#tune-the-run}

| Réglage | Champ du modèle de configuration | Option |
|---|---|---|
| Comptes analysés simultanément (4 par défaut) | `max_concurrent_accounts` | `--max-concurrent-accounts` |
| Secondes autorisées par compte (1800 par défaut, au moins 60) | `account_processing_timeout` | `--account-processing-timeout` |
| Un compte à la fois | `parallel_processing: false` | `--disable-parallel-processing` |

Si un compte échoue, par exemple parce que son rôle ne peut pas être assumé,
InvenTag journalise l’erreur et rapporte les comptes qui ont fonctionné. Il ne
se rabat pas sur vos identifiants par défaut pour ce compte. La feuille `Summary`
du rapport Excel et le rapport Word ont une section « Run notes » (notes d’exécution) qui nomme chaque compte non analysé et la raison.
Le journal contient la même liste :

```text
1 account(s) were not scanned, or only partly. The report does not include them:
  - 222222222222 (Dev): Context establishment failed: Role assumption failed for account 222222222222: An error occurred (AccessDenied) when calling the AssumeRole operation: ...
```

L’exécution se termine toujours avec le code 0. Ajoutez `--fail-on-account-error` pour terminer avec le code 5
quand un compte n’a pas pu être analysé complètement. Les rapports sont quand même écrits.
Si tous les comptes échouent, l’exécution se termine avec le code 1 et n’écrit aucun rapport.

Un compte qui manque de temps (`--account-processing-timeout`) compte comme en échec, mais les ressources qu’il a trouvées
avant la limite restent dans le rapport, et les notes indiquent que le compte est incomplet.
Voir [Limite de temps et comptes en parallèle](./run-a-scan.md#time-limit-and-parallel-accounts).

## Continuer après un échec {#continue-after-a-failure}

InvenTag enregistre les comptes qui ont terminé. Une fois la cause corrigée, relancez la même commande avec `--resume` pour n’analyser que les autres :

```bash
inventag --accounts-file accounts.yaml --create-excel --resume
```

InvenTag réutilise les résultats enregistrés de la même commande (mêmes comptes, régions, services et filtres) qui ne sont pas
plus anciens que `--resume-max-age-hours` (24 par défaut, 168 au maximum).
Voir [Reprendre après une exécution en échec](./run-a-scan.md#continue-after-a-failed-run).

## Dans un pipeline GitLab CI/CD {#in-a-gitlab-cicd-pipeline}

Non vérifié sur un runner GitLab ni sur un vrai compte AWS : ce pipeline n’a pas été exécuté sur GitLab. Son YAML et sa ligne de commande `inventag` sont contrôlés lors de la construction de la documentation. Son job a été exécuté en local avec gitlab-ci-local 4.77.1 (avec un substitut de rsync) contre un AWS simulé, avec un jeton factice.

Ce job analyse tous les comptes de `accounts.yaml` selon une planification de pipeline. Il se connecte à un seul rôle via OIDC, puis InvenTag assume le rôle `InvenTagReadOnly` dans chaque compte. Le job utilise `--resume` : le cache et un **Retry** peuvent donc terminer les comptes qui manquaient. `accounts.yaml` est versionné dans le dépôt ; il ne doit donc contenir que des ID et des noms de compte, et aucune clé d’accès. Avant de l’utiliser :

- Créez le rôle auquel GitLab se connecte et la variable CI/CD `AWS_ROLE_ARN`, comme décrit dans [Exécuter InvenTag en CI/CD](../guides/run-in-ci.md#gitlab-cicd). Cette même section explique comment créer la planification du pipeline.
- Donnez à ce rôle `sts:AssumeRole` sur le rôle `InvenTagReadOnly` de chaque compte, et faites en sorte que chacun de ces rôles lui fasse confiance : voir [Configurer un accès en lecture seule](./read-only-access.md#with-an-iam-role-in-each-account). Le fichier de politique `config/defaults/iam-policy-read-only.json` ne contient aucune instruction `sts:AssumeRole` ; vous devez donc en ajouter une.

```yaml
# .gitlab-ci.yml
stages:
  - inventory

org-inventory:
  stage: inventory
  image: python:3.12
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule"
    - if: $CI_PIPELINE_SOURCE == "web"
  timeout: 3 hours                            # the ID token expires with the job
  id_tokens:
    GITLAB_OIDC_TOKEN:
      aud: sts.amazonaws.com
  variables:
    AWS_DEFAULT_REGION: us-east-1
  cache:
    key: inventag-state
    paths:
      - bom_output/state/                     # saved results of finished accounts, for --resume
    when: always                              # save them when the job fails, too
  script:
    - pip install "inventag-aws==%INVENTAG_VERSION%"   # pin a release
    - export AWS_WEB_IDENTITY_TOKEN_FILE="$(mktemp)"
    - printf '%s' "$GITLAB_OIDC_TOKEN" > "$AWS_WEB_IDENTITY_TOKEN_FILE"
    - |
      inventag --accounts-file accounts.yaml --cross-account-role InvenTagReadOnly \
        --create-excel --resume --resume-max-age-hours 12 \
        --fail-on-account-error --fail-if-empty
  artifacts:
    when: always                              # keep the reports of the accounts that worked
    paths:
      - bom_output/
    expire_in: 30 days
```

Les lignes que tous les exemples GitLab ont en commun sont expliquées dans [Exécuter InvenTag en CI/CD](../guides/run-in-ci.md#gitlab-cicd). Ce tableau couvre ce qui est propre à cet exemple.

| Élément | Ce qu’il fait |
|---|---|
| `--accounts-file accounts.yaml --cross-account-role InvenTagReadOnly` | Le job se connecte à un seul rôle via OIDC. À partir de là, InvenTag assume le rôle `InvenTagReadOnly` dans chaque compte du fichier. |
| `cache:` avec `key: inventag-state`, `paths: - bom_output/state/`, `when: always` | InvenTag enregistre les comptes terminés dans `bom_output/state/partial/` ([Reprendre après une exécution en échec](./run-a-scan.md#continue-after-a-failed-run)). Un nouveau job démarre avec un dossier vide : le cache transporte donc `bom_output/state/` jusqu’au job suivant. `when: always` enregistre le cache lorsque le job échoue ; par défaut, il n’est enregistré qu’en cas de succès ([GitLab : `cache:when`](https://docs.gitlab.com/ci/yaml/#cachewhen), [GitLab : caching](https://docs.gitlab.com/ci/caching/)). |
| `--resume --resume-max-age-hours 12` | Après une exécution en échec, cliquez sur **Retry** sur le job (ou attendez la prochaine exécution) : seuls les comptes manquants sont analysés. Le `12` est voulu. Avec la valeur par défaut de 24 heures, l’exécution de la nuit suivante pourrait réutiliser les résultats de la nuit précédente d’une exécution en échec. Sans résultats enregistrés, `--resume` ne change rien. Si le cache est absent, tous les comptes sont analysés de nouveau : plus lent, jamais faux. Les règles de réutilisation des résultats enregistrés sont dans [Reprendre après une exécution en échec](./run-a-scan.md#continue-after-a-failed-run). |
| `--fail-on-account-error --fail-if-empty` | Code de sortie 5 lorsqu’un compte n’a pas pu être analysé ; code de sortie 6 lorsqu’aucune ressource n’a été trouvée. Les rapports des autres comptes sont écrits et conservés par `artifacts: when: always` ([GitLab : `artifacts:when`](https://docs.gitlab.com/ci/yaml/#artifactswhen)). |
| `timeout: 3 hours` | La durée maximale d’un job sur les runners hébergés par GitLab de GitLab.com ([GitLab : hosted runners](https://docs.gitlab.com/ci/runners/hosted_runners/)). |

Éléments que l’exécution locale n’a pas couverts :

- Non vérifié sur GitLab ni sur AWS : l’émission du jeton d’ID par GitLab et son acceptation par AWS pour le rôle, avec les conditions de la politique d’approbation sur `aud` et `sub`.
- Non vérifié sur GitLab : `image`, `timeout`, `expire_in` et `cache` (gitlab-ci-local les ignore).
- Non vérifié sur une planification de pipeline GitLab : l’exécution locale a défini l’origine du pipeline à la main.
- Non vérifié sur AWS : le rôle OIDC qui assume le rôle `InvenTagReadOnly` dans chaque compte, avec de vraies politiques d’approbation.

## Vérifier le fichier de comptes {#check-the-accounts-file}

InvenTag lit le fichier de comptes comme du texte UTF-8, avec ou sans marque d’ordre des octets, de 1 Mio au plus.
Il s’arrête avec le code de sortie 1 et nomme le problème quand :

- le fichier est vide, ou son niveau supérieur est une liste et non un ensemble de paires `clé: valeur` ;
- une clé est écrite deux fois (le message donne la ligne, par exemple `accounts file accounts.yaml:3: duplicate key 'accounts'`) ;
- le type de fichier n’est ni `.json`, ni `.yaml`, ni `.yml` ;
- un compte n’a pas d’`account_id` non vide, ou un champ a un mauvais type.

Si le fichier contient `secret_access_key` ou `session_token` et que d’autres utilisateurs peuvent le lire, InvenTag avertit et vous dit d’exécuter `chmod 600`.
Utilisez `profile_name` ou `role_arn` plutôt que des clés. Vérifiez un fichier sans analyser :
`inventag --accounts-file accounts.yaml --validate-config-only --skip-credential-validation`.

Deux erreurs d’options arrêtent l’exécution avec le code de sortie 2 : `--accounts-file` avec `--accounts-prompt`,
et un ARN de rôle complet dans `--cross-account-role` avec un fichier de comptes (donnez-y un nom de rôle, ou mettez `role_arn` dans le fichier).
